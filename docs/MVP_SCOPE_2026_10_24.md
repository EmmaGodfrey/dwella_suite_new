# Agreed MVP scope — 24 October 2026

This records the module-by-module agreement with the user. It defines the intended release scope; it does not claim that the remaining features are implemented. It supersedes earlier suggestions to defer tenant self-service, payment collection, bulk imports or SMS/WhatsApp reminders. Reports is excluded from this review and improvement work.

Preserve existing page structures, especially Maintenance. Reuse the current working product and approved document designs. Design new or substantially changed screens in Figma for review before frontend implementation. Continue in small, focused increments; no push or deployment is authorised by scope agreement.

## Module agreement

| Module | Agreed MVP |
| --- | --- |
| Account access and setup | Existing sign-in, recovery, profile and optional two-factor authentication; working welcome/reset delivery; existing business/property/unit setup and checklist; a short optional first-use tour with skip/replay |
| Properties and units | Property details/photo, units/rent, search/filtering, occupancy linked to leases, editing/history safeguards; bulk unit import with a template, preview, duplicate/error checks and confirmation |
| Tenants and self-service | Manager contact/identity records, search, active/past filtering, lease/unit/balance context, archive without losing history and bulk tenant import; tenant access to their own dashboard, invoices, payment history/receipts, lease/signing/downloads, maintenance and contact profile |
| Leases and documents | Lease terms, start/end lifecycle, approved branded agreement/PDF previews/downloads, designated manager and tenant signing, retained versions/records and originals; simple Renew lease copies details into a new draft, updates dates/rent and collects fresh signatures while retaining history |
| Billing, payments and receipts | Recurring rent invoices, one-off charges, partial/full payment, actual mobile-money and card collection through the chosen Lenco by Broadpay provider, provider-confirmed statuses, duplicate protection, receipts/history, manual recording and reasoned corrections |
| Payment visibility | Managers see collected amounts, applicable fees, net amounts, destination accounts and payout/settlement status from actual provider data; platform administrators control integration configuration |
| Maintenance | Tenant requests/photos linked to their tenancy; manager requests for units/shared areas; priority/status/vendor assignment, scheduling/access permission, comments/progress, costs, completion notes and appropriate tenant charges; preserve the four-lane board/list and completed history |
| Dashboard | Manager view of expected/collected/outstanding rent, occupancy, lease expiries and open repairs; tenant view of their balance, Pay action, lease and maintenance updates; link figures to the relevant existing records |
| Notifications and communication | In-app, email, SMS and WhatsApp reminders/updates; manager-triggered messages to a tenant or selected tenant group, recipient/content preview, explicit confirmation and delivery history; the same scoped action through the assistant where authorised |
| Admin and beta tools | Existing users/workspaces/suspension, identity review, explicit audited support access and beta onboarding/invitations; configure Lenco/email/SMS/WhatsApp, inspect payment/message failures and delivery status; retain the current admin structure |
| Future subscription readiness | Central workspace feature access and optional record limits, enforced on the backend and available to frontend hooks; keep the pricing model, paid feature selection, tier names and subscription billing provider undecided |

Tenant email remains optional for basic manager-entered contact records; electronic lease signing requires the fixed recipient email. Portal account access must securely link a user to the correct tenancy. Being a tenant account type or having a navigation label does not establish that the tenant portal is already delivered.

Some features will be paid. The user has not chosen unit-based/flat/other pricing, tiers or subscription collection arrangements. Keep access policy separate from roles and payment providers, preserve current beta defaults and historical records, and avoid building a checkout or announcing prices before those decisions. See [SUBSCRIPTION_READINESS.md](SUBSCRIPTION_READINESS.md) for the implemented foundation and integration contract.

Signing uses email verification, explicit consent, signing timestamps, fixed document versions and retained records. The user explicitly agreed to defer certificate-based digital signatures. Mailbox verification must not be described as verified legal identity. Signing and tenancy activation remain separate actions.

## External decisions and verification

- **Payments:** Lenco by Broadpay is selected. Verify official APIs, merchant/settlement arrangements, supported mobile-money/card routes, fee information, confirmation/webhook verification and onboarding requirements before implementing collection. Provider selection alone does not establish account readiness or the permitted routing of customer funds.
- **SMS:** no provider is selected. Africa's Talking Zambia is the first candidate researched; Twilio's Zambia route is an alternative. Compare current per-segment prices, Airtel/MTN/Zamtel coverage, branded sender registration and delivery reports before choosing. No provider has been contacted or purchased through this review.
- **WhatsApp:** choose/configure an official Business Platform connection, obtain recipient opt-in and prepare approved templates for business-initiated sends. Manager-triggered messages must respect the platform's template/service-window constraints.
- **Email:** verify configured delivery for account recovery, lease signing and manager messages, including sender identity and reply handling. Platform credentials stay outside manager screens.
- **Documents:** managers provide complete approved lease wording and issuer/signatory details. The visual proposal is not a supplied legal template.

Provider references researched during this review: [Africa's Talking Zambia](https://zambia.africastalking.com/), [Twilio Zambia SMS](https://www.twilio.com/en-us/guidelines/zm/sms), [WhatsApp Business Messaging Policy](https://business.whatsapp.com/policy). Recheck current integration requirements before building.

## Later scope

Certificate-based digital signatures; autopay; automatic bank matching; cross-invoice allocations; automated refunds and deposit settlement; full accounting/expense ledger; inspections and recurring maintenance; vendor portal/procurement; complex approvals; live chat; advanced CRM/screening; custom dashboards/forecasting; complex role hierarchies; subscription billing automation; multiple interchangeable providers; and a universal document library.

The broader product inventory remains useful context, but a missing item there is not automatically a launch requirement. Existing implemented capabilities are not to be removed simply because their expansion is deferred.

## Proposed delivery order

1. Review the existing Figma references against this agreed scope; design the tenant experience, new import/renewal flows, payment states and communication/admin controls. Include the short guided tour without moving existing page sections.
2. Implement tenant account/tenancy boundaries and self-service data access, then bulk imports and renewal with their integrity checks.
3. Integrate Lenco collection, confirmations, receipts and manager destination/settlement visibility after the provider model is verified.
4. Add scheduled/on-demand communication and operational controls after SMS/WhatsApp/email setup decisions are resolved.
5. Complete the tour and cross-module checks in staging using designated test recipients/accounts, then prepare a reviewable release.

This order is an implementation proposal, not a claim of additional user decisions. Backend security work follows plan → implement → validate, with relevant permission/failure/concurrency tests. Frontend work requires production builds and checks of the touched desktop/mobile flows. No live messages, real charges, provider purchases or deployments are part of design review.
